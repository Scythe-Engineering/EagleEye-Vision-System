# Live-device latency investigation — 2026-09-08

A one-line publisher setting reduced camera-timestamp-to-WPILib-robot-loop latency
from **82.7 ms mean / 131.0 ms p95** to **34.8 ms mean / 46.7 ms p95**.
An independent second 60-second optimized window measured **35.4 ms / 46.6 ms**.
The optimized publisher is installed and running on `eagleeye@100.84.225.35`.

## Change

`src/secondary_operations/publish_to_networktables.py` now creates publishers with
`PubSubOptions(keepDuplicates=True, sendAll=True, periodic=0.01)`.
Previously `periodic` was omitted, using the installed ntcore default of 0.1 seconds.
All samples and duplicate values are still preserved, as are capture timestamps.
No detector, camera, calibration, field map, pose gate, or pipeline setting was changed.
Only this publisher file was copied to the Pi; its existing unrelated edits were preserved.

[WPILib's publish/subscribe documentation](https://docs.wpilib.org/en/stable/docs/software/networktables/publish-and-subscribe.html)
defines the default 100 ms interval and distinguishes a publisher's outgoing cadence
from a subscriber's requested server cadence. A subscriber change alone would not
fix this client publisher's outgoing batching. No Java SDK change was necessary.

A temporary passive Java recorder drained the actual live Pose3d/meta queues in
`robotPeriodic`, and recorded the existing SDK diagnostic observations after its
exact-timestamp join. Each duration is Java `NetworkTablesJNI.now()` minus the
incoming capture timestamp, translated by NT4 into the server clock. No remote
wall-clock subtraction was used. The Java TimedRobot loop runs every 20 ms.
The recorder did not request a faster subscription or change quality gates.

This measures the physical camera's **reported capture timestamp through the Pi
pipeline, Tailscale, NT4, and Java robot-loop consumption**. It is not an independently
measured photon-to-actuator or camera-to-browser-display latency. V4L2 timestamps
can represent end-of-frame rather than start-of-exposure; absolute exposure timing
and clock-sync error were not independently calibrated. Network delay asymmetry
can affect the synchronized timestamp estimate.

The real stationary camera is not mechanically coupled to the simulated drivetrain.
It remains on the separate diagnostic channel, while the bench's synthetic vision
feeds its simulated drivetrain estimator. No physical actuator was commanded.

Mean improvement: 57.9%; p95 improvement: 64.3% in the first optimized window.
Arrival batches changed from approximately 12 frames to 2–3 frames per robot loop.
Baseline samples extending beyond the SDK's age limit did not all reach its
diagnostic output. Optimized windows had a diagnostic observation for every raw pose.

Production-quality observations remain zero because the current map/calibration
produces about **2.74 px reprojection error**, exceeding the unchanged 2 px gate.
The existing separate 4 px diagnostic channel is used for observation only; it is
not a recommendation to loosen the production threshold.

A 30-second sample of 99 existing profiler snapshots measured:

| Pi metric | Mean, ms | p95, ms |
| --- | ---: | ---: |
| Flow execution | 5.12 | 5.87 |
| Cycle, including capture wait | 7.30 | 10.99 |

The remaining roughly 20 ms between average Pi completion age and Java consumption
includes send scheduling, transport, and the 20 ms robot loop. These independently
sampled means are a rough budget, not a per-frame decomposition. The browser's
pipeline latency is only the Pi-side metric; its displayed FPS is not a measurement
of delivery rate at the robot. Intermittent 129–136 ms tails remain and were not
isolated to a particular network or scheduling component.

Pi→Mac ping: 8/8 replies, mean 9.55 ms RTT, maximum 23.86 ms. Pi throttling flags
were `0x0`, temperature 46–49 °C; an optimized system snapshot showed 33.2% CPU.
